# Ory's official Java client for Hydra's admin API

## Context and Problem Statement

`faye-host-hydra` talks to Hydra's admin API with hand written HTTP and JSON: `HydraFlowHost` (load, accept and reject login, consent and logout requests) and `HydraClientDirectory` (list clients, following `Link: rel="next"`; [ADR 0015](0015-oauth2-client-management.md)), about 260 lines on `java.net.http` and Jackson. The user decided (2026-10-31) to use Ory's official client instead, so request and response shapes come from Hydra's published API description rather than our reading of it.

Facts checked while deciding:

* Ory publishes `sh.ory.hydra:hydra-client` on Maven Central, generated by OpenAPI Generator (okhttp and Gson). Versions include `2.2.0` and `2.2.1`; newer ones follow Ory's new release numbering (`25.4.0`, `26.2.0`).
* The stack pins Hydra `v2.2.0` (image digest in `deploy/compose.yaml`, checksums in `deploy/hydra-local.sh`).
* Its `2.2.0` POM depends on okhttp, logging-interceptor, Gson, gson-fire, commons-lang3, jsr305, swagger-annotations, jackson-databind-nullable, Apache Oltu's OAuth2 client (retired by Apache), jsr311-api and javax.ws.rs-api, with jakarta.annotation-api as `provided`.

## Decision Drivers

* The engine never imports Hydra (AGENTS.md rule 3): the client stays inside `faye-host-hydra`, behind `FlowHost` and `ClientDirectory`.
* Behaviour on the wire stays the same: the same requests, the same accept and reject bodies, and the same mapping into `HostRequest`.
* `-Xlint:all -Werror` and NullAway still pass.
* Smallest dependency footprint that works.

## Considered Options

* `sh.ory.hydra:hydra-client` 2.2.0, matching the pinned server
* `sh.ory.hydra:hydra-client` at the newest release (26.x)
* Keep the hand written client

## Decision Outcome

Chosen option: **`sh.ory.hydra:hydra-client` 2.2.0**, the same version as the pinned server. The client, the image digest and the `hydra-local.sh` checksums move together.

* `faye-host-hydra` depends on it as `implementation`, so nothing leaves the module. `jakarta.annotation-api` (Boot managed) is `compileOnly` so javac can read the generated classes without warnings, as `org.jetbrains:annotations` is for webauthn4j ([ADR 0004](0004-identity-dependencies.md)).
* Excluded transitive dependencies, which Faye never uses because the admin API is called without OAuth: Apache Oltu's OAuth2 client, `jsr311-api`, `javax.ws.rs-api`. If any code path we use needs them, the tests fail and this exclusion is revisited.
* One `ApiClient` per host, base path the admin URL, with 10 second connect, read and write timeouts, as before.
* Free form objects (`client.metadata`, `context`) come back from Gson as maps whose numbers are all `Double`. They are converted to plain Java values with integral numbers as `Integer` or `Long`, as Jackson produced before, so a predicate or hook sees `2`, not `2.0`.
* Tests run both classes against a local HTTP stub and assert the exact paths, methods and JSON bodies the hand written client sent, written before the switch.

### Consequences

* Good, because paths, parameters and bodies come from Hydra's published API, and new admin API features need no hand written HTTP.
* Bad, because the client brings okhttp, Gson and gson-fire into the server: a second JSON library beside Jackson.
* Neutral: generated models could reject fields they do not know. Checked for 2.2.0 (2026-10-31): `OAuth2LoginRequest` and `OAuth2Client` carry `additionalProperties` (`getAdditionalProperties`, `putAdditionalProperty` in the jar's classes), so unknown fields are kept, not rejected. The client and the server version still move together.
* Bad, because Ory's numbering changed after 2.2.x; upgrading Hydra means moving to a 25.x or 26.x client, with an API review.

### Confirmation

`cd server && ./gradlew build` passes, with `HydraClientDirectoryTest` and a `HydraFlowHost` test asserting the recorded requests. On a fresh compose stack, `deploy/smoke.sh` passes (sign ins through the ten applications, consent, and the Applications list).

Run on 2026-10-31: `cd server && ./gradlew build` passes (`HydraClientDirectoryTest` 3, `HydraFlowHostTest` 7); `deploy/smoke.sh` passes on a fresh compose stack.

## Pros and Cons of the Options

### hydra-client 2.2.0

* Good, because its models match the server we run.
* Bad, because of the dependency tree above, part of it old.

### hydra-client 26.x

* Good, because it is maintained.
* Bad, because it targets a newer Hydra than the one we pin; using it means upgrading Hydra first, which is a separate decision.

### Keep the hand written client

* Good, because it has no dependencies beyond the JDK and Jackson, and it works.
* Bad, because every shape is our reading of Hydra's API, checked only by our own tests.
